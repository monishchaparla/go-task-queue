go-task-queue

A distributed background-job queue in Go, designed so that killing a worker mid-job never loses the job, and proven with chaos tests.

Status: Planned — implementation not started yet. This page describes the plan. Nothing here has been built, and no performance numbers exist.

The problem

Slow or failure-prone work (emails, webhooks, reports) belongs outside the request path. A background queue has to say what happens when a worker crashes halfway, when a producer retries an enqueue, or when a job fails every time. The plan is a small, readable queue that answers these correctly and checks the answers by killing processes.

What it will do

gRPC and HTTP enqueue

Producers submit jobs over gRPC, with a small HTTP/JSON surface for convenience.

Leases with visibility timeouts

Workers lease jobs and can extend the lease by heartbeat. Stale workers are fenced out by a lease token.

At-least-once delivery

Accepted jobs run at least once or end in the dead-letter queue. Idempotency keys dedupe enqueues.

Retries and DLQ

Exponential backoff with jitter, then a dead-letter queue with replay.

Scheduled jobs

Delay a job until a given time.

Metrics and dashboard

Prometheus metrics and a small built-in dashboard.

Architecture (planned)

Workers talk only to a stateless queue server. The server owns every state change in the database, so delivery rules live in one place.

  1. Producers call Enqueue over gRPC or HTTP.
  2. Queue server (any number of replicas) validates and writes to storage; a reaper loop requeues expired leases.
  3. PostgreSQL holds the jobs table; jobs are claimed with FOR UPDATE SKIP LOCKED.
  4. Workers call Lease, Heartbeat, Ack, Nack on the server.
  5. Prometheus scrapes the server; the dashboard reads the same stats.

Job states: ready → leased → done, or back to ready with backoff, or to dead after the last allowed attempt. The full Mermaid diagrams are in the README.

Chosen for v1: Postgres. The goal is reliability, so effort goes to delivery semantics and tests. A log-backed store is a stretch goal, to be compared with measurements behind the same interface.

Guarantees and chaos tests

  • At-least-once, not exactly-once: a job may run twice, so handlers must be idempotent.
  • Planned chaos tests kill workers mid-job, stop the server, and restart the database under load.
  • They will assert that every acknowledged job ends as done or dead, that none are lost, and that duplicates are counted rather than hidden.

Benchmark plan

To be measured after correctness is established: enqueue and end-to-end throughput (jobs/sec), end-to-end latency p50 and p99, and recovery time after a worker kill. Open-loop load for latency, repeated runs, and hardware recorded with every result. No results exist yet.
